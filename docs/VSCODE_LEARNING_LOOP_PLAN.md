# Trainer × VS Code 学习闭环开发方案

日期：2026-09-08  
状态：设计基线 v1；本地配对、工作区授权与课程实践静态评审已装配到本机生产链路；真实课程首次提交、受控执行、云同步与 Windows 端仍待独立验收/实现。  
范围：先打通本地项目绑定、题目驱动提交、可追踪评估和可信统计。本文中的新接口、表和界面均为待实现设计，不代表已经可用。

## 1. 产品目标与非目标

用户在自己的 VS Code 中完成项目练习，Trainer 负责教学、收集经授权的材料、评审、引导修改和记录进展。绑定后不重复选择文件；点击“提交并检查”即可形成一次明确、可查看的提交。

- 保留 macOS 原生 SwiftUI。后端协议独立于 UI，未来 Windows 原生客户端复用同一业务服务。
- 共用后端代码与 API 不等于已有云服务；本阶段仍使用本地 Gateway，没有云账号、跨设备同步或远程部署。
- 本阶段不开发独立 IDE，不依赖 VS Code 私有内部接口，不抓取每次按键，不监控其他工作区。
- GitHub 为后续独立阶段；不在本阶段读取仓库、建立 OAuth 授权或上传代码。
- 不把提交次数、在线时长、GitHub 活跃度直接当作编程能力。

## 2. 已核对的现状与缺口

| 现有位置 | 已有能力 | 缺口 |
|---|---|---|
| `vscode-trainer-extension/src/extension.js` | 用户触发命令，发送选区、语言、相对路径和当前文档诊断 | 没有持续工作区绑定、配对认证、多文件提交；当前请求含 `autoGenerate: true`，教学生成与同步耦合 |
| `gateway/learning_store.py` | SQLite 凭据、进度、经验、活动和成就 | 类型由客户端提供；凭据计数不是评估通过数 |
| `gateway/assessments.py` | 按课评估文本答案，验证引用存在，提供 0–4 分反馈 | 独立于保存入口；覆盖旧评估而非保存尝试历史；不处理文件快照和多文件定位 |
| `TrainerApp.swift` / `LessonAssessment.swift` | 记录入口、类型选择、单独评估入口 | 出题、提交、反馈、进度和统计未成为一个事务性闭环 |
| `gateway/model_transport.py` | 统一 AI 传输、密钥隔离、连接诊断 | 需接入新任务的会话、取消、超时与结果校验 |

不得把现有选区命令描述为已接通完整 IDE，也不得把旧凭据迁移成“已验证通过”。

## 3. 核心用户流程

1. VS Code 执行“连接 Trainer”，与本地应用进行配对。
2. Trainer 展示工作区、课程及权限范围；用户首次确认绑定。
3. AI 按课程生成练习契约：类型、目标、提交材料、评分标准和通过条件。
4. 用户在 IDE 编写代码。Trainer 显示明确任务及“需要提交什么”，不进行后台云端实时评估。
5. 用户点击“提交并检查”。绑定与外发授权仍有效时，无须再次选择文件。
6. 本地收集相关材料、检查敏感信息、冻结快照；界面展示文件数量、范围摘要和可展开清单。
7. 保存提交后启动异步评估；用户可继续操作，不丢失答案。
8. 反馈关联具体文件和原快照行号；用户可跳转 IDE、修改并再次提交。
9. 首次满足练习通过条件后更新完成状态、经验和统计；给出“下一练习”。

“返回课程去记录”入口改为“继续练习”，不再让用户自由选择统计类型。没有当前练习时先选择课程，不为统计造一条空练习。

## 4. 题目驱动的练习契约

每份练习至少包含以下字段，服务端保存不可变修订版：

| 字段 | 约束 |
|---|---|
| `exerciseId`, `revision`, `lessonId`, `planId` | 稳定标识，关联有效课程；修改评分标准必须产生新修订 |
| `kind` | `reflection / reading / writing / debugging / transfer`，模型按题目声明，服务端校验；提交端不能修改 |
| `prompt`, `learningObjectives` | 可理解的题目和具体目标 |
| `submissionSpec` | 必需答案、代码、报告，以及各项是否可选；缺材料时不调用评分 |
| `contextHints` | 相关模块、文件模式和依赖提示；仅作为建议，不授予文件访问权限 |
| `rubric`, `passRule` | 可核对的评价维度、条件和必要证据；不能提交后临时改变标准 |
| `verificationRequirement` | `static_review / user_report / trusted_execution`，决定需要什么级别的证据 |

出题时校验类型与材料要求是否相容。例如编写题不能只要求一句回讲。模糊或校验失败的题目先修复，不能靠客户端关键词猜测统计类型。

回讲、阅读题只显示必要的文本输入；代码题默认从绑定工作区收集；调试题明确要求现象、修复说明及可用结果。支持“暂无运行报告”，但不能因此满足要求运行验证的通过条件。

## 5. 项目绑定、配对与权限

- Gateway 仅监听回环地址；所有新增状态修改和材料读取接口必须认证，不能仅凭来自 localhost 判断可信。
- 应用确认一次性配对码；服务端颁发限定作用域的扩展令牌。码短期有效、限次验证；令牌可撤销，不放在 URL、日志或仓库中。
- 扩展令牌使用扩展安全存储，AI 密钥仍只由 Gateway 获取；扩展不能读取 AI 密钥。
- 绑定记录包括用户、工作区 ID、规范化根目录、课程、授权版本、允许的文件范围和外发目的地。
- 分开授权“读取本地项目”和“向当前 AI 服务发送相关材料”。首次可选择持续授权，以免每次确认。
- 切换服务商/目的地、绑定新根目录或扩大范围时重新确认。仅重复提交已授权范围不弹确认框。
- 多根工作区逐根授权；远程 SSH、容器、WSL 的路径不能当成本机路径读取。本阶段明确提示暂不支持，后续通过扩展传输适配。
- 失联、撤销、工作区不可信时停止采集；撤销后不能继续上传已排队但未外发的内容。

## 6. 自动材料采集与多文件提交

### 6.1 采集规则

以练习相关文件和相对上次提交的变更为起点，补入相关接口、配置及测试文件。不能只发 diff 导致缺上下文，也不能默认发送整个项目。

- 首次无基线：按练习范围建立快照；不要求项目必须有 Git。
- 有 Git 时可使用受控的只读变更查询；不执行 hook，不修改分支，不自动暂存或提交。
- 未保存编辑内容默认提示保存或明确使用编辑器快照；不能默默用磁盘旧内容评估。
- 文件新增、重命名、删除以清单事件表示；已删除文件不被当成仍然存在。
- 读取后记录内容哈希，评估只使用冻结快照；随后修改标记为“提交后有新变更”。
- 边界检查使用规范路径；防止 `..`、符号链接越界及读取过程中的路径替换。按需安全打开文件并校验对象。
- 默认排除密钥、`.env`、证书、凭据文件、依赖、构建产物、二进制和无关目录；`.gitignore` 不能代替安全排除规则。
- 敏感检测命中后阻断相关文件外发并说明原因；不声称检测能发现所有秘密。
- 初始限制：单文件 256 KiB、单次最多 100 文件/2 MiB UTF-8 文本。超限进入“需要缩小范围”，不静默截断或偷偷拆成无限收费请求。

### 6.2 用户界面

默认一个主按钮“提交并检查”；旁边显示“将检查 N 个文件＋答案”。可展开查看清单、排除原因和本次变化，不强制逐个勾选。

提交时发现新敏感内容、越界或缺少关键材料才打断。自动收集不等于用户失去预览和撤销权。

### 6.3 代码与日志定位

快照保存相对路径、文件哈希、行号基准与材料来源。AI 返回的路径和行号必须在快照内存在；否则作为无定位反馈处理，不生成错误跳转。

点击“在 VS Code 中查看”由已配对扩展打开已授权工作区内文件。当前内容不同于快照时显示差异提示，不误把旧行号当作当前准确位置。

## 7. 调试材料与执行边界

| 来源 | 可以说明什么 | 不能说明什么 |
|---|---|---|
| VS Code 文档诊断 | 诊断提供器报告的错误、警告 | 程序已运行成功、所有依赖正确 |
| 用户附加日志/测试报告 | 用户提供了某次运行材料 | Trainer 亲自执行或结果不可伪造 |
| AI 静态评审 | 提交代码在评审中的问题与推断 | 实际测试已通过 |
| 受控执行记录（后续） | 指定环境、命令、快照和退出状态的实测结果 | 未执行路径或生产环境的安全性 |

首版支持批量代码和报告文件，不要求逐文件粘贴，不承诺通用读取终端历史或所有测试扩展结果。VS Code 能力需通过公开扩展 API 验证，不能依赖私有实现。

首版不自动运行导入项目的安装、构建和测试命令。后续受控执行须单独评审：命令参数、工作目录、网络、环境变量、超时、进程取消、报告来源及用户授权。AI 给出的命令只是建议，不能直接执行。

## 8. 提交、评估与反馈状态机

`draft → collecting → blocked | queued → evaluating → passed | needs_revision | insufficient_evidence | failed | cancelled`

- `blocked`：权限、范围或材料不满足；展示明确修复项，不收费评估。
- `queued/evaluating`：展示当前阶段、耗时、最后更新时间；不伪造百分比。重复点击返回同一提交。
- `passed`：满足该题既定标准；同时显示实际验证级别，不笼统称“运行验证通过”。
- `needs_revision`：给出可行动修改，按严重性排序并指向材料。
- `insufficient_evidence`：不能凭空判错；告诉用户缺什么。
- `failed/cancelled`：保留材料，不增加通过数，可显式重试。

每次提交携带幂等键；重试同一网络请求不产生新尝试。用户修改后重新提交生成新 attempt，关联父提交并仅新增变化快照。外部 AI 费用无法保证 exactly-once：崩溃后未知状态不盲目重发，显示费用可能重复并要求显式重试。

评估结果包括 rubric 分项、证据引用、问题定位、下一步、验证来源和模型/规则版本。后端验证结构、引用、评分范围和通过条件；模型不能自行更新数据库或执行工具。

反馈成功落库后，同一事务写入练习结果、奖励账本和统计事件。断电恢复不得出现“显示通过但经验未记”或重复奖励。

## 9. 数据模型与接口草案

新增表：`workspace_bindings`、`extension_pairings`、`exercises`、`submissions`、`submission_files`、`assessment_results`、`learning_events`、`reward_ledger`。

- 关系：练习 1:N 提交；提交 1:N 文件；提交 1:N 评估执行记录。保留尝试历史，不删除前一次评估。
- 文件内容按哈希存储，引用清单记录来源；清理时只删除没有引用的对象。
- 唯一约束：提交幂等键；奖励 `(learner_id, exercise_id, reward_kind)`。改题修订不自动再奖励。
- `schema_version` 支持数据库迁移；备份包括绑定描述、题目、提交和统计，不包含令牌/API 密钥。恢复后重新配对，不能沿用失效机器路径授权。

拟定 `/v2` 接口：

| 接口 | 用途 |
|---|---|
| `POST /pairings`、`POST /pairings/confirm` | 发起配对、应用确认（不同权限） |
| `POST /workspace-bindings`、`DELETE /workspace-bindings/{id}` | 绑定与撤销 |
| `GET /exercises/{id}` | 读取当前有效题目契约 |
| `POST /submissions` | 冻结材料并创建幂等提交，返回 202 和任务 ID |
| `GET /submissions/{id}` | 轮询阶段、材料清单和反馈 |
| `POST /submissions/{id}/cancel`、`POST /submissions/{id}/retry` | 明确取消/重试 |
| `GET /learning-summary` | 带来源、分母和版本的统计 |

契约实施前必须形成 JSON Schema/OpenAPI、统一错误码和请求大小限制；不得依靠这份草案直接猜字段开发。

## 10. 统计与历史迁移

- 分开显示：尝试数、已评数、首次通过的练习数、待改进数、评估失败数。
- 类型从服务端题目读取；按练习去重计算通过率，分母明确为已完成有效评估的独立练习。
- 活动图保留“提交记录”口径；练习通过图单独展示，不能混淆。
- 语言图展示已评练习覆盖范围、数量和验证来源；缺评估显示待评估，不用次数填充分数。
- XP 首次通过练习奖励建议 10 XP；历史自述 XP 作为历史积累保留，不追扣、不伪造通过。新旧来源在账本中区分。
- 成就注明依据“提交”还是“通过”，不在升级时悄悄改变旧徽章的含义。
- 历史 evidence 迁移为 `legacy_self_report`，历史 assessment 为 `legacy_ai_review`。保留原内容和时间，不能反推不存在的练习、测试结果或 IDE 活动。

## 11. 严格开发流程与分阶段交付

每阶段遵循：现状核对 → 契约/威胁模型 → 失败测试 → 最小实现 → 回归与安全检查 → 实机验收 → 记录已知限制 → 才进入下一阶段。

| 阶段 | 交付物 | 完成门槛 |
|---|---|---|
| P0 设计基线（本轮） | 本文、现状与范围 | 明确待实现事项，不改业务数据 |
| P1 契约与迁移 | Schema、数据迁移、事件/奖励唯一约束、固定测试数据 | 空库/旧库迁移与回滚测试通过，备份可恢复 |
| P2 安全绑定 | 扩展配对、工作区授权、状态指示、撤销 | 未认证、越界、失联、跨工作区访问被拒绝 |
| P3 自动提交 | 多文件快照、排除规则、增量材料、提交流程 | 无 Git、未保存文件、大项目、重命名/删除均可解释处理 |
| P4 评估闭环 | 自动类型、统一提交按钮、异步评估、引用定位、修改重试 | 真实多文件练习完成一次提交→修改→通过；失败不丢材料 |
| P5 统计与体验 | 去重统计、完成标识、反馈跳转、图表来源 | 同题多次提交不刷 XP，重启后记录一致 |
| P6 GitHub（后续） | 独立授权与隐私设计后只读接入 | 用户批准具体权限；不把 commit 数等同能力 |
| P7 Windows（后续） | 独立原生 UI、共用契约和业务层 | Windows 实机验证路径、凭据存储、进程及安装升级 |

P6/P7 不是 P1–P5 的依赖。不承诺本轮完成云端、GitHub 或独立 IDE。

## 12. 验收与测试矩阵

1. **单元测试**：类型不能被提交端篡改；rubric 校验；路径穿越；符号链接；密钥排除；大小边界；引用合法性；奖励去重。
2. **集成测试**：扩展→Gateway→快照→模拟 AI→评估→统计；跨工作区拒绝；重复提交；撤销队列；服务重启恢复。
3. **故障测试**：401/403/429、超时、截断响应、格式错误、磁盘写满、取消竞态、AI 返回未知文件、评估过程中源文件改变。
4. **迁移测试**：旧凭据和分数保留来源；重复运行迁移无副作用；备份恢复后需重新配对。
5. **实机体验**：回讲、阅读、多文件编写、附报告调试各一条；反馈跳转；空状态；连接断开；窄窗口；键盘导航；减少动态效果。
6. **安全验证**：项目 README、源码注释、日志中的指令仅作不可信材料；不得触发任意命令、文件访问或变更授权。
7. **网络实测**：默认使用固定材料和 mock，不自动重复收费请求；端到端调用仅使用用户已授权的目的地与材料范围。

## 13. 发布与完成定义

每阶段保留测试结果、接口变化、数据库版本、未覆盖场景和回滚说明。启用新提交流程前完成备份，旧记录只读可见。上线前核对无进行中的任务，不能为更新强行丢弃用户提交。

“完整闭环已完成”必须同时满足：真实工作区安全绑定、无需逐文件选择、材料可追溯、评估反馈可定位、修改可重试、统计去重、重启恢复、旧数据迁移、端到端验收通过。只有页面或接口存在不算完成。
